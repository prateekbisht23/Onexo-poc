claude-code-poc · system notes

Onexo Architecture

A browser chat UI where every conversation gets its own hardware-isolated KVM microVM on AWS, running Claude Code headless — backed by a persistent S3 volume, so the VM is disposable but the files and history are not. The AWS box is reached only through an SSH tunnel.

01 · the whole system

One map, two machines

Everything lives on two machines. Your Mac runs the chat surface: the React frontend and the Bun backend. An EC2 instance in Mumbai runs CubeSandbox, and this is where Claude actually lives — each conversation gets a throwaway micro virtual machine with Claude Code running headless inside it, plus a persistent S3 volume mounted at /home/user/projects that survives the VM. The only way traffic moves between the two is an SSH tunnel — the AWS box exposes nothing to the internet except port 22.

02 · the chat plumbing

How a message flows

The default backend is SANDBOX=cubesandbox — one VM per conversation:

  1. The browser keeps one WebSocket open to the Bun backend and sends {"type":"chat","text":"…"}.
  2. On the first message of a conversation the backend creates the session's S3 volume (POST /volumes {name, driver:"s3"}) and boots a claude-code-template microVM with it mounted at /home/user/projects (volumeMounts on POST /sandboxes). One root-level chown user:user makes the mount writable — that fix persists on the volume.
  3. Inside the VM, a persistent headless Claude Code process is started via envd: claude -p --input-format stream-json --output-format stream-json, working directory on the volume. Your message is written to its stdin; there is no per-message process startup.
  4. Claude's output streams back as JSON events (token by token), which the backend relays to the browser unchanged. After every turn the backend syncs the transcript (<session-id>.jsonl) out of the VM.
  5. The sidebar's SQLite db stores ids, titles, the volume name, and the tenant (org/user) — never the messages.

Model access is chosen per user with /login: OneXO (claude calls the OneXO AI gateway — Kong /llm/anthropic → Connectra — through a reverse tunnel, with the user's own short-lived OneXO token fetched by its apiKeyHelper from the backend) or the user's own Anthropic account (direct, CLAUDE_CODE_OAUTH_TOKEN). No credential is written into the VM. The legacy docker mode (SANDBOX=docker) still exists — Claude in the local claude-poc container, with a run_code MCP tool that executes code in one-shot microVMs; the VM mode doesn't need that tool, since Claude's whole shell is already inside a VM.

03 · persistence & resume

The life of a conversation

Because the files live on the volume, killing a VM costs nothing. That inverts the old teardown problem: instead of keeping VMs alive to protect state, the backend kills them freely and recreates them on demand.

Teardown policy

  • Never close on task-done — a conversation is many turns; the VM stays warm between them.
  • Idle timeout ~5 min (VM_IDLE_TTL_S=300) — lossless now, so it can be short.
  • Hard cap 2 h (SANDBOX_SESSION_TIMEOUT_S=7200) as a runaway safety net.
  • LRU eviction at capacity (MAX_LIVE_VMS=3 on this box) — a new session evicts the least-recently-used idle VM instead of blocking; the evicted session just resumes later.
  • User controls: "End session" kills the VM and keeps the volume; "Delete conversation" also destroys the volume.

Tenancy

Every volume and VM action is scoped through one function, getIdentity() in server/index.ts, which returns {org, user} — stubbed from headers/env in the PoC, backed by JWT/SSO in production with the same signature. Volumes are named vol-<org>-<user>-<id>, and the backend is the only thing that ever talks to the Cube API, so two users can never see each other's volumes. Decisions, scaling path, and the cost model live in docs/persistent-sessions.md.

04 · trick one

PVM: microVMs on a cloud VM that has no KVM

CubeSandbox normally needs /dev/kvm — hardware virtualization. But an EC2 instance is already a virtual machine, and AWS doesn't pass hardware virtualization through to it. Tencent's answer is PVM (Pagetable Virtual Machine): a modified host kernel whose kvm_pvm module provides a software implementation of the KVM interface, so microVMs run inside an ordinary cloud VM with near-native speed.

operational warning

The stock PVM kernel has no AWS ENA network driver — one was custom-built into it during setup. Upgrading the PVM kernel without rebuilding the ENA driver leaves the instance unreachable. Snapshot before touching the kernel.

05 · trick two

Host-header routing: reaching a VM that has no address you can resolve

Creating a sandbox is easy — that's just the Cube API on tunneled port 3000. The hard part is talking to the sandbox afterwards. Every interaction with a running VM — starting Claude, writing to its stdin, reading files, watching the file tree — goes through envd, an agent on port 49983 inside each VM, addressed as 49983-<sandboxID>.cube.app. That hostname is resolved by a DNS server that only exists on the EC2 box. Your Mac has never heard of it.

One related discovery, learned the hard way: the modern official e2b JS SDK (v2+) can't talk to this deployment at all — it calls POST /v2/sandboxes, which CubeSandbox answers with 405. So the backend speaks the v1 REST API directly with plain fetch. The same lesson repeated with volumes: the SDKs' ergonomic volume_mounts map is not the wire format — the API wants volumeMounts: [{name, path}], and an unknown field is silently ignored (you get a 201 and no mount).

Isolation, upgraded

In the old design Claude lived in a local Docker container and only the code it ran got a microVM. Now Claude itself runs inside the microVM — its own kernel, on a different machine, per conversation. A container shares the host's kernel; a microVM does not. The blast radius of anything Claude does is one VM plus one volume, both scoped to one tenant, and the VM is destroyed routinely.

Operational notes

  • The EC2 box fits ~4 lean VMs (~3 GB each after control-plane overhead); the backend enforces MAX_LIVE_VMS=3 and LRU-evicts idle VMs at capacity — losslessly, since files persist.
  • Capacity frees ~10 seconds after a VM is killed; a create issued too soon gets no more resource. The client retries automatically.
  • Stop, never terminate, the instance when idle (free-tier credits). The public IP changes on every stop/start — update the tunnel command.
  • The Cube API has no auth configured — acceptable only because the security group admits nothing but SSH from one IP. Never open 3000/80/12088 to the internet as-is.
  • Scaling out = add Cubelet worker nodes (control plane is stateless) + move the backend's conversation registry to Redis. Full plan and cost model: docs/persistent-sessions.md.
